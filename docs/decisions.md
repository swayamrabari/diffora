# Decisions

Short ADR-style log. Each entry records a decision that affects the build.

## 2026-11-17 — Next.js 16 uses `proxy.ts`

- Context: Next.js 16.4.6 deprecates `middleware.ts` and renames the convention to `proxy.ts`. Proxy defaults to the Node.js runtime.
- Decision: Use `web/src/proxy.ts` for the fast session-cookie check and page redirects. Keep full user lookup and authorization in the Node data-access layer.
- Consequences: `proxy.ts` must not import Prisma or bcrypt. Page layouts and API routes remain authoritative for auth.

## 2026-11-17 — Cache Components disabled

- Context: The scaffold enables `cacheComponents` and `partialPrefetching`. The app is authenticated and request-dependent.
- Decision: Set `cacheComponents: false` and remove `partialPrefetching`. Mark the authenticated layout dynamic and instantiate Prisma lazily.
- Consequences: Simpler auth pages and no build-time database access. Revisit only if caching becomes a requirement.

## 2026-11-17 — Raw engine output stored as text

- Context: PostgreSQL `jsonb` does not preserve key order or whitespace, so a `Json` column cannot hold “unmodified” engine output.
- Decision: Store exact stdout in `Comparison.rawDiffText` (`Text`) and its UTF-8 byte length in `rawDiffBytes`. Parse it only for export.
- Consequences: Exports can be checked against the engine. Storage grows with comparison size; the caps in the spec bound it.

## 2026-11-17 — Pin oasdiff 1.38.0 and disable external refs

- Context: The local `oasdiff` was a `main` build, and remote `$ref` loading is an SSRF risk.
- Decision: Pin `v1.38.0`, verify its SHA-256, and pass `--allow-external-refs=false` to both engine commands. Pre-scan for non-fragment `$ref` and absolute `$id` as defence in depth.
- Consequences: Specs with external refs are rejected with `EXTERNAL_REF_NOT_SUPPORTED`; engine exit `123` must be mapped explicitly. The version and hashes live in `docs/notes.md`.

## 2026-11-17 — Fixture files may contain JSON

- Context: Most fixtures are easiest to generate as JSON objects; JSON is valid YAML 1.2, and the engine accepts it.
- Decision: Store object fixtures as JSON text in `base.yaml` / `target.yaml`. Use hand-written YAML for YAML-specific fixtures (`yaml-quirks`, `yaml-anchors`, `external-ref`, `invalid-target`).
- Consequences: The parser sees the same document either way. YAML-specific coverage remains explicit.

## 2026-11-17 — Fixture generation is reproducible

- Context: Thirty-one pairs with overlapping schemas are easy to drift by hand.
- Decision: Generate them with `docs/day1/generate-fixtures.mjs`; keep `raw.expected.json` and `validation.json` as committed evidence.
- Consequences: Regenerating fixtures is one command. Review raw expected diffs before committing changes.

## 2026-11-17 — Failed comparisons are first-class

- Context: A failed comparison needs to be reopened and re-run, but the v1 error response exposed no identifier.
- Decision: Create the failed `Comparison` row and include `details.comparisonId` in the error response.
- Consequences: The Compare dialog can navigate to the failed record and offer “Run again”.

## 2026-11-17 — Cookie `Secure` is configuration, not `NODE_ENV`

- Context: Docker Compose runs a production build on plain HTTP; a `Secure` cookie would not be sent and login would break.
- Decision: Use `COOKIE_SECURE` (default `false` locally, `true` for HTTPS).
- Consequences: Local and production behaviour are explicit. Deployment must set it correctly.

## 2026-11-17 — Use oasdiff changelog/summary/breaking directly

- Context: The full normalizer (`usedBy`, component attribution, dedup, side-aware refs, `DetectedChange` rows) is a large amount of code for a demo. oasdiff 1.38.0 already emits structured JSON for changelog, summary, and breaking changes.
- Decision: `/diff` runs four pinned commands in one temp directory and returns `rawDiffText`, `changelog`, `summary`, `breaking`, and a small `deprecations` subset extracted from `diff`. The database stores those JSON/text fields instead of per-change rows.
- Consequences: Severity/level labels are now part of the product. The UI is a flat changelog explorer with Summary, Changes, Breaking, Deprecations, and Source diff tabs. Component-level grouping, `usedBy`, and before/after values require a future thin diff extractor if needed. The change is recorded at the top of `DIFFORA.md`.

## 2026-11-17 — Prisma 7 with the PG adapter

- Context: Prisma 7 uses the `prisma-client` generator, an explicit generated output path, and driver adapters for PostgreSQL.
- Decision: Use `prisma-client` with output `src/generated/prisma`, `@prisma/adapter-pg`, and `prisma7.config.ts`. CLI commands use `DIRECT_URL`; the runtime client uses `DATABASE_URL` through the adapter.
- Consequences: The generated client is gitignored and regenerated by `predev`/`prebuild`. Prisma CLI requires a `.env.local` or `.env` file; `prisma7.config.ts` loads `.env.local` first.

## 2026-11-18 — Structured deduplicated changes

- Context: Changelog findings are operation-oriented and cannot provide before/after values or reliable type grouping. The raw diff contains the values, types, and component copies.
- Decision: The Go service now builds a structured `changes` array from the raw diff, follows `$ref` to canonical component pointers, deduplicates by change type + base/target pointer, and returns it with the existing outputs. The web stores rows in `ComparisonDiffChange`.
- Consequences: The Changes tab is type-first and shows before/after values; operation copies collapse to one component change. `ComparisonFinding` remains for readable changelog/breaking rows. Older comparisons without structured rows are flagged for re-run.

## 2026-11-17 — Duplicate findings grouped in the workspace

- Context: oasdiff changelog repeats shared-schema and security changes once per operation. The test pair has 109 findings but only 58 unique source changes by rule + line/column.
- Decision: Keep raw findings rows and group in the client by `ruleId + level + line + column`, falling back to `ruleId + level + text` when no source location exists. Show variants and affected endpoints inside each group. Provide a toggle to show every raw finding.
- Consequences: The default Changes/Breaking view is much shorter without hiding data. No schema or ingest changes are needed. A grouped row can represent several endpoint copies, so the detail panel lists all variants and endpoints.

## 2026-11-17 — Comparisons are stored as findings rows

- Context: Changelog and breaking output can contain thousands of items. Reopening must not call oasdiff, and the UI needs filtering and pagination.
- Decision: On a successful `/diff`, store one `Comparison`, one `ComparisonFinding` row per changelog/breaking item, one `ComparisonDeprecation` row per deprecation, plus `summary` JSON and exact `rawDiffText`. Store failed comparisons with zero counts and a sanitized error code.
- Consequences: Reopening reads PostgreSQL only. Findings filters use indexed columns. Changelog and breaking duplicate a subset of rows, which is accepted for simple tab queries. The full workspace is Phase 5; Phase 4 has a minimal comparison page.

## 2026-11-17 — Upload metadata parsed in the web app

- Context: The thin Go service passes YAML/JSON to oasdiff and no longer extracts metadata. The web app still needs `openapi`, `info.title`, and the format for storage and display.
- Decision: Parse metadata in the web app with the `yaml` package for YAML and `JSON.parse` for JSON. Call the Go service `/validate` for engine validation. Store the original decoded text.
- Consequences: The web app owns metadata parsing and the engine owns validation. Uploads fail if either parser rejects the file. The web and engine must agree on supported OpenAPI versions.

## 2026-11-17 — Deprecations use the diff walker

- Context: oasdiff has no dedicated deprecations command. `changelog` reports endpoint deprecations, but a diff walker can read every `deprecated` flag with exact old/new values.
- Decision: Keep `internal/deprecations`, derive deprecations from the raw `diff`, and store them in `ComparisonDeprecation` rows. Do not filter deprecations from changelog text.
- Consequences: The service has one small JSON walker and one extra table, but the Deprecations tab has exact pointers, paths, methods, and presence flags for operation, component, and property deprecations. The changelog remains the source for the Changes and Breaking tabs.

## 2026-11-17 — Findings are rows, not one JSON blob

- Context: Changelog and breaking output can contain thousands of items. One JSON column would make filtering and pagination awkward.
- Decision: Store each changelog/breaking item as a `ComparisonFinding` row with a `kind` column. Store deprecations as `ComparisonDeprecation` rows. Keep `summary` as JSON and `rawDiffText` as text on `Comparison`.
- Consequences: The UI can filter by level, section, rule, operation, and path with indexed queries. Breaking items duplicate a subset of changelog rows; this is accepted for simplicity and can be changed to an `isBreaking` flag later.

## 2026-11-17 — Thin proxy, same-format comparisons

- Context: The v2 service converted YAML to JSON, extracted metadata, and pre-scanned external refs, duplicating work oasdiff already does. The app only needs the four engine outputs.
- Decision: Write uploaded YAML/JSON as-is and pass it to oasdiff. Require both compared versions to use the same format; return `400 FORMAT_MISMATCH` for mixed YAML/JSON. Return JSON-only results. Store `rawDiffText` as text, `summary`/`deprecations` as JSON, and changelog/breaking items as `ComparisonFinding` rows.
- Consequences: The service is much smaller and has no YAML parity surface. The UI can filter findings with SQL instead of parsing one large JSON blob. Mixed-format comparisons are intentionally rejected.

## 2026-11-18 — One diff command, one changes array, one workspace

- Context: Running `diff`, `changelog`, `summary`, and `breaking`, then storing findings, structured changes, and deprecations separately, duplicated the same information in the service, database, and UI. The tabs made the product harder to use than the underlying comparison.
- Decision: The Go service runs only `oasdiff diff -f json --allow-external-refs=false`. It returns `engineVersion`, `durationMs`, and one deduplicated `changes` array. The web app stores that array in one JSONB `changes` column plus `totalChanges` on `Comparison`, drops `ComparisonFinding`, `ComparisonDiffChange`, and `ComparisonDeprecation`, and renders a single-page workspace with a collapsible summary, filters, a grouped tree, and one unified diff.
- Consequences: Deprecated is a tag/filter, not a tab. Breaking, Deprecations, Source diff, raw findings, and technical pointers are removed from the product. This supersedes the multi-output, per-finding table, grouping, and tab decisions above. The reference pair stores 83 unique changes, and pointers remain internal only.

## 2026-11-18 — Full-line source hunks

> Superseded by the next entry: context padding was removed.

- Context: The value diff showed only the changed scalar (for example `80 → 120`), but users need to see the complete line and its surrounding spec context.
- Decision: Map each change's resolved base/target pointer to a position-aware YAML/JSON node, then attach a `source` diff with full lines, old/new line numbers, and 3 context lines above and below. Modified blocks are line-diffed, so unchanged lines stay as context. Pure additions/removals use the full node range.
- Consequences: Every change for the reference pair now has source hunks. While adding this, array-index and category bugs in required/enum/tag/security/header pointers were fixed, surfacing 15 real changes that were previously collapsed; the reference pair now reports 83 unique changes. Large hunks are capped at 600 lines with a gap marker. Old comparisons without source hunks fall back to the value diff.

## 2026-11-18 — Focused hunks without padding

- Context: Diffing a 3-line window around each change highlighted neighboring changes as if they belonged to the selected change, and nearby changes could consume the padding. It also made simple scalar changes noisy.
- Decision: Use only the exact base/target node range for each change. Added/removed blocks show every line; modified blocks are line-diffed inside the exact range and emit only `removed`/`added` lines. No surrounding context is emitted. Separated changed regions become separate hunks.
- Consequences: Each sidebar entry now shows exactly one change with no unrelated highlights and no missing padding. The line numbers still locate the change. Older comparisons with context rows continue to render, but new comparisons produce only changed lines.

## 2026-11-18 — Type sidebar with full-width change cards

- Context: The nested change tree made it hard to scan a category and see the actual diffs. The page also scrolled as a normal document instead of feeling like a full-height commit review.
- Decision: Replace the tree with a sidebar that lists change types and counts. Selecting a type renders that type's changes as full-width cards, each with its own focused source diff. The header stays fixed below the app bar, and the sidebar/detail split fills the remaining viewport height with independent scrolling.
- Consequences: The comparison page no longer scrolls past the workspace. The detail area is a card list, filters live above the cards, and the tree/group-by controls are gone. No database or API changes were required.

## 2026-11-18 — Slim header and comparison cards

- Context: The dashboard repeated recent comparisons, the project page used a dense table, and the comparison page had a second large header on top of the workspace. The product felt congested.
- Decision: Use one slim app header style across the app. The dashboard keeps totals and projects only. The project page renders comparisons as cards with added/removed/modified/deprecated summaries and a **View changes** action. The comparison route hides the global top bar and owns a slim header with the Diffora logo, project, and file labels, followed only by the type sidebar and card detail area.
- Consequences: The comparison page is a single full-viewport surface with no redundant header or summary block. The project page is easier to scan, and the dashboard no longer duplicates comparison data.

## 2026-11-18 — Full-width shell and semantic badge colors

- Context: The app was capped at a narrow max width, card side-stripes carried the change-type color, category badges were visually flat, and diff line numbers/markers did not share the code color.
- Decision: Remove the max-width cap from the app shell and top bar. Replace card side-stripes with green/red/violet change-type badges and a separate palette for category badges. Match the code block background to the card, and use the same font, size, and color for line numbers, the `+`/`-` marker, and code.
- Consequences: All pages use the full viewport width with responsive padding. The comparison cards are cleaner, category colors are distinct from change-type colors, and diff rows read as a single visual unit. The card list has extra bottom scroll padding.

## 2026-11-18 — Fixed header, neutral type tags, tighter code blocks

> Superseded by the next entry: code-block padding was restored to a uniform value.

- Context: The header still shifted between pages and carried dashboard/export/delete actions. Colored category badges competed with change-type colors, and code blocks had container padding that made the first/last rows look detached.
- Decision: Make the app header sticky with a fixed brand / conditional breadcrumb / user layout. Remove the Dashboard link and header actions. Move export/delete into project comparison cards. Make category and subtype tags neutral; keep only change type colored. Remove top/bottom code-block padding and apply it to the first/last diff rows instead.
- Consequences: The header stays visually stable across dashboard, project, version, and comparison pages. Comparison actions live with the comparison card. Type tags are quieter, and diff rows own their spacing so the code block background stays continuous with the card.

## 2026-11-18 — Uniform code padding and compact mono breadcrumb

- Context: First/last row padding made short code blocks feel uneven, the header had more horizontal padding than needed, and breadcrumb items mixed weights and colors.
- Decision: Restore uniform code-block vertical padding and remove the per-row first/last padding. Reduce header horizontal padding. Style the conditional breadcrumb path in a single mono size, weight, and color.
- Consequences: Code blocks have an even vertical rhythm regardless of line count. The header is tighter, and the path reads as one consistent monospace label.

## 2026-11-18 — Two-tag cards and soft-rounded badges

- Context: Cards showed change type, category, parameter location, and sometimes a deprecated tag. The extra tags competed with the change itself, and pill-shaped badges felt too rounded for the rest of the UI.
- Decision: Show only two tags per card: change type and category. Remove the subcategory and deprecated tags from the card header. Change the shared badge radius from pill to `rounded-md`, including project/version status and summary tags.
- Consequences: Cards scan faster and keep the change-type color meaningful. Deprecated changes remain filterable and their titles still say “Marked deprecated”; they no longer add a third tag. All badges now share a softer rectangular shape.
